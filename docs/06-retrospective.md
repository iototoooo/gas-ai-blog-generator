## 2. 工夫した点

1. **「失敗しても安全な側に倒れる」設計**
   投稿作成リクエストは自動再送せず、次回実行時にスラッグ検索で「実は作成済み」を検出する方式にした。リトライによる二重投稿を構造的に防げる。
2. **ステータスとロックの組み合わせ**
   ロックはステータス変更の瞬間だけ取り、API 呼び出し中は保持しない。長時間ロックを避けつつ、「生成中」ステータスで二重実行を防いだ。
3. **GAS 6分制限を前提にした処理単位**
   締め切りオブジェクトを全処理で共有し、再試行の待機時間まで残り時間内に収める。止まった処理は10分で「停止」とみなしてリセットできる。
4. **AI の出力を信用しすぎない**
   JSON Schema で形式を固定したうえで、コード側でも文字数・見出し数・説明文・丸写しを検証。仕様外は具体的な数値を添えて書き直させる。
5. **コストと時間の上限を「回数」で縛る**
   時間の上限だけでは、短い応答の失敗が続いた場合に課金が膨らむ。1記事あたりのAPI呼び出しを4回に制限し、応答時間5〜120秒×6種類の障害パターンで、5件一括処理でも6分を超えないことをテストで確認した（最悪270秒）。
6. **ローカルで完結するテスト**
   GAS のサービス（スプレッドシート・UrlFetchApp・LockService 等）をインメモリでモックし、外部ライブラリなしでテストを実行できる（2026-11-18 時点で162件）。実APIを呼ばずに、429・529・401・タイムアウト・応答拒否などの異常系まで再現した。

## 3. 課題・リスク

| 課題 | 影響 | 対応方針 |
|---|---|---|
| 実環境の検証範囲 | 主な流れは確認済み。異常系（誤ったAPIキー、一括生成の時間上限、WordPress 側の事前下書きとの紐付け）は実環境では未確認 | 残りの B テスト（docs/04-testing.md）を実施 |
| Haiku 5.5 の文章品質 | 5本中4本は仕様内。文字数は下限寄り（平均 約2,187）で、1本は不足。Sonnet との比較は未実施 | 同じキーワードで Sonnet と比較し、既定モデルを最終決定（B-21） |
| 1回の API 応答時間の想定 | 時間上限の計算は「1回の応答が約2分以内」を前提 | 実環境で応答時間を計測し、必要なら `PER_ARTICLE_BUDGET_MS` を調整 |
| UrlFetchApp の応答待ち上限 | 長文生成で通信タイムアウトの可能性 | `CLAUDE_EFFORT=low`、モデル変更で調整。必要なら記事を分割生成する方式を検討 |
| 文字数の数え方 | 「2,000〜3,000文字」の定義（空白除外・見出し込み）は本システムの仕様 | 講座・クライアントの定義と異なる場合は `countArticleChars_` を調整 |
| 停止判定の日時解析 | 「処理開始日時」を JST 前提で解析 | `appsscript.json` のタイムゾーンを Asia/Tokyo 固定にして対応 |
| 列の手動変更 | 列を挿入するとデータがずれる | マニュアルで禁止を明記。将来は見出し名で列を特定する方式に |
| 共有時の秘密情報 | スプレッドシートの編集者は Script Properties を閲覧可能 | 編集権限を限定する運用を手順書に記載 |

## 5. 実環境テストでの学び

正式5テーマの記事生成テスト（2026-11-17〜18、Haiku 5.5、プロンプト v2）の結果です。詳細は [テスト記録](04-testing.md#実施結果) を参照してください。

- **生成時間**：1回の生成で約30秒、書き直しを含めると約57秒でした。6分の実行上限には余裕があります。
- **文字数**：1,995〜2,368文字（平均 約2,187）でした。書き直しは5本中1本（G-1）で、2回目も5文字足りませんでした。目安（2,500）より短くなりやすい傾向があります。
- **費用**：5本の合計は $0.021151、1本あたり約 $0.003〜0.004 でした。書き直しが起きると約2倍になります。
- **WordPress 連携**：テスト用 WordPress（TasteWP）で、接続・アプリケーションパスワード認証・下書き保存（投稿ID 7）・シートへの記録・二重投稿の拒否を確認しました。法令を扱わない KW-002 で行い、公開はしていません。

**学んだこと**
1. **仕様の判定と、内容の正しさは別物**：G-1 は文字数が足りないのに「生成済み」になっていました（修正済み）。「OK」の記事でも、法令の記述が正しいかは人が確認しないと分かりません。
2. **「断定しない」指示の副作用**：法令の数値を創作させないための指示が、正しい数値まで書かせない結果になりました。36協定の記事では、検索意図の中心である上限時間が抜けていました。安全のための制限が、記事の価値を下げることがあります。
3. **単純なキーワード判定の限界**：「仮の数値」のチェックは、法令の数値・日付にも反応しました。警告が多すぎると、利用者が警告を読まなくなる危険があります。
4. **改善の方向**：AI に事実を「思い出させる」のではなく、人が公的資料で確認した情報を渡して、それだけを使わせます（[法令情報の正確性と公開判断](09-legal-accuracy.md)）。

### GAS・Claude API・WordPress の連携で学んだこと
1. **状態をシートに持たせると、連携の失敗に強くなる**：「生成中」「投稿中」などのステータスと投稿IDをシートに記録しておくと、同じ記事の再投稿を WordPress に送る前に止められます。実環境の再投稿テストでも、通信の前に `INVALID_STATE` で拒否されました。
2. **外部サービスは段階的につなぐ**：ローカルのモックテスト → clasp での配置と読み取り比較 → Claude API で1本生成 → 5本生成 → テスト用 WordPress、の順に進めました。問題が見つかったときに、どの段階の問題かをすぐ特定できました。
3. **WordPress 側の設定は環境ごとに違う**：アプリケーションパスワードは、https のサイトでないと使えない場合や、プラグインで無効化されている場合があります。最初に「WordPress接続テスト」で権限まで確認できるようにしたことで、下書き保存の前に設定の問題を切り分けられました。
4. **公開はシステムに任せない**：下書き（draft）固定にし、公開は人が WordPress 上で行う設計にしました。AI の記事、とくに法令を扱う記事は人の確認が必要なため、この線引きは運用上も必要でした。
5. **秘密情報はコードとシートの外に置く**：APIキー・アプリケーションパスワード・スクリプトIDは Script Properties と Git 管理外のファイルにだけ置きました。配置やテストを何度繰り返しても、値が Git やログに残りませんでした。
